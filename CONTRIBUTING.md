# Contributing

Thanks for taking the time to contribute!
This guide describes the practices used in this repository.

## Getting started

You need Node.js >= 22 and Docker. The tests start real MongoDB servers with [Testcontainers](https://node.testcontainers.org/).

```bash
git clone https://github.com/ggrossetie/db-migrate-mongodb.git
cd db-migrate-mongodb
npm ci
npm test
```

Run a single test with a name pattern.

```bash
node --test --test-name-pattern="<pattern>" test/mongodb.test.js
```

The CJS bundle (`bundle.cjs`) is generated by `npm run build`. It is built automatically before publishing, so you do not need to commit it with your change.

## Making a change

1. Create a branch from `master`, named after the kind of change (`fix/dry-run`, `feat/state-management`, `ci/release-workflow`...).
2. Add or update tests. A bug fix comes with a test that fails without the fix.
3. Add an entry to the `Unreleased` section of the [changelog](#changelog) when the change is visible to users.
4. Update the `README.md` when the behavior or the configuration changes.
5. Open a pull request against `master`. The CI runs the tests on Node.js 22 and 24.

Keep pull requests focused. One pull request should cover one fix or one feature.

### Tests

The driver is tested against every supported environment, so a change must pass on all of them.

- MongoDB server 6.0, 7.0 and 8.0 (`test/mongodb.test.js`)
- db-migrate 0.11 and 1.9, through the API and the CLI (`test/db-migrate.test.js`)

Every public method supports both a callback and a promise (it returns a promise when no callback is provided). Keep both when you add or change a method.

A method that writes to the database must go through the `_write()` helper, so the operation is logged and skipped with `--dry-run`.

### Commit messages

Commit messages follow the [Conventional Commits](https://www.conventionalcommits.org/) format.

```
<type>: <description>

<optional body, explaining why the change is needed>
```

| Type    | Usage                                              |
|---------|----------------------------------------------------|
| `feat`  | A new feature                                      |
| `fix`   | A bug fix                                          |
| `doc`   | Documentation only                                 |
| `test`  | Tests only                                         |
| `ci`    | CI and release workflows                           |
| `chore` | Maintenance (dependencies, tooling, packaging...)  |

Write the description in the imperative mood, in lower case and without a trailing period, for instance `fix: honor --dry-run in write operations`.

## Semantic versioning

This package follows [Semantic Versioning](https://semver.org/). Given a version `MAJOR.MINOR.PATCH`,

- `MAJOR` is incremented for breaking changes, such as dropping a Node.js version, dropping a major version of the `mongodb` peer dependency, or changing the signature or the behavior of a public method in an incompatible way
- `MINOR` is incremented for new features that are backward compatible, such as supporting a new major version of `mongodb` or of db-migrate
- `PATCH` is incremented for bug fixes that are backward compatible

Prereleases use a suffix (`2.1.0-beta.1`). They are published on npm with the `testing` dist-tag, so they never replace `latest`.

The public API is made of the `connect()` function, the methods of the driver available in migrations, and the configuration options documented in the `README.md`. Methods prefixed with an underscore are internal, except `_getDbInstance()`.

## Changelog

The `CHANGELOG.md` file is written by hand, for the users of the package. It is not generated from the commit messages.

Add your entry at the top of the file, in the `Unreleased` section, under one of these headings.

```markdown
## Unreleased

### Breaking Changes

* ...

### Features

* ...

### Bug Fixes

* ...
```

A few guidelines.

- Describe the change from the point of view of a user, not the implementation.
- Link the issue when there is one, for instance `([#2](https://github.com/ggrossetie/db-migrate-mongodb/issues/2))`.
- Explain how to migrate when the change is breaking.
- Skip the changes that users cannot see (refactoring, tests, CI).

Do not rename the `Unreleased` section and do not bump the version in `package.json`. The release workflow takes care of both.

## Releases

Releases are fully automated by the [Release workflow](.github/workflows/release.yml). Nothing is published from a developer machine.

To release, a maintainer picks the next version according to the content of the `Unreleased` section and the [semantic versioning](#semantic-versioning) rules, then runs the workflow from the `master` branch with the version, without the `v` prefix.

```bash
gh workflow run release.yml --ref master -f version=2.0.1
```

The workflow then

1. validates the version and runs the tests
2. bumps the version in `package.json` and `package-lock.json`
3. renames the `Unreleased` section of the changelog to `<version> (<date>)` with [@bestikk/changelog](https://www.npmjs.com/package/@bestikk/changelog)
4. commits, tags (`v<version>`) and pushes to `master`
5. publishes the package to npm with [provenance](https://docs.npmjs.com/generating-provenance-statements), authenticated through OIDC ([Trusted Publisher](https://docs.npmjs.com/trusted-publishers)), so no npm token is stored in the repository
6. creates the GitHub release, using the changelog section as release notes

A version with a suffix is published as a prerelease, on npm (`testing` dist-tag) and on GitHub.
